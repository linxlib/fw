# FW Framework Documentation

## Overview

FW is a lightweight Go web framework designed for fast API development. It uses annotation-style comments to describe routes and middleware, builds on top of `fasthttp`, and includes in-repo AST parsing, dependency injection, unified responses, and OpenAPI generation.

Module path:

```go
github.com/linxlib/fw/v2
```

Runtime dependencies:

- `github.com/valyala/fasthttp`
- `github.com/fasthttp/router`
- `github.com/pterm/pterm`
- `gopkg.in/yaml.v3`

## Main Features

- Annotation-based route registration
- Controller, service, and middleware auto-registration
- Global, controller-level, and method-level middleware
- Deterministic middleware merge and execution order
- Request-scoped dependency injection
- Automatic binding for path, query, header, and body parameters
- Built-in request context helper
- Automatic handler return serialization plus a unified JSON response envelope with pluggable formatter/encoder
- Panic recovery and request logging
- Automatic OpenAPI document generation and Swagger UI
- `cmd/fw` CLI for project creation, build flow, and code scaffolding

## Quick Start

### 1. Create a project

```bash
fw init demo
cd demo
```

What `fw init` creates:

- `main.go`
- `controllers/`
- `services/`
- `middlewares/`
- `models/`
- `config/app.yaml`
- `.gitignore`

The generated `go.mod` module name is the project or directory name. If you want a full module path like `github.com/you/demo`, update `go.mod` after initialization.

### 2. Generate metadata and build

```bash
fw build
```

`fw build` performs three steps:

1. Runs `go generate ./...`
2. Generates `.astp.json` and `fw_autoreg_gen.go`
3. Builds the binary and prints artifact size and SHA-256

### 3. Run in development

```bash
go run .
```

Important: the scaffolded project embeds `.astp.json`, so you should run `fw build` or `go generate ./...` at least once before `go run .`.

## Basic Project Structure

- `app/`: engine lifecycle, controller registration, routing, runtime dispatch
- `annotation/`: normalized annotation access
- `astp/`: AST parser and auto-registration generator
- `inject/`: dependency injection container and invoke pipeline
- `config/`: YAML config plus environment overrides
- `logger/`: colored console logger and optional file output
- `context/`: request context wrapper
- `middleware/`: middleware interfaces and chain execution
- `response/`: default envelope, formatter, encoder
- `openapi/`: OpenAPI generation and Swagger routes
- `cmd/example/`: working example project
- `cmd/fw/`: framework CLI

## How the Framework Starts

Typical startup code:

```go
package main

import (
	_ "embed"

	"github.com/linxlib/fw/v2/app"
)

//go:generate go run github.com/linxlib/fw/v2/astp/cmd/astp -exported .

//go:embed .astp.json
var astpData []byte

func main() {
	e, err := app.New("config/app.yaml")
	if err != nil {
		panic(err)
	}

	e.EmbedProject(astpData)

	if err := e.ListenAndServe(); err != nil {
		panic(err)
	}
}
```

At runtime, `Engine` does the following:

1. Loads configuration
2. Loads project metadata from source code, `.astp.json`, or embedded AST data
3. Applies auto-registrars generated by ASTP
4. Collects routes and middleware bindings
5. Registers HTTP handlers
6. Generates `openapi.json` and Swagger routes when enabled

## Annotation System

FW uses Go comments such as `// @GET /users` and `// @Authorization(Admin)`.

Supported annotation styles:

- `@X`
- `@X value`
- `@X(a,b)`
- `@X(k=v, role=admin)`

Handler-specific response annotations used by the framework include:

- `@Response(...)`: choose which return value drives the OpenAPI response schema
- `@RawResponse`: write the first non-`error` return value directly without the default `code/message/data` envelope

## Controller Usage

Define a controller type with `@Controller` and optionally `@Route`.

```go
package controllers

import (
	"github.com/linxlib/fw/v2/context"
	"github.com/valyala/fasthttp"
)

// UserController handles user APIs.
// @Controller
// @Route /api/v1/users
type UserController struct{}

// GetUser returns one user.
// @GET /:id
func (c *UserController) GetUser(ctx context.Context, id string) error {
	return ctx.Respond(fasthttp.StatusOK, 0, "ok", map[string]any{
		"id": id,
	})
}
```

Rules:

- `@Route /base` or `@Route(/base)` defines the controller base path
- Method-level HTTP annotations define routes under the base path
- Supported HTTP annotations are `@GET`, `@POST`, `@PUT`, `@DELETE`, `@PATCH`, `@OPTIONS`, and `@HEAD`
- One method may declare multiple same-method routes if the URLs are different
- Duplicate `METHOD + PATH` registrations are rejected

Example:

```go
// @POST /user
// @POST /user_info
func (c *UserController) ModifyUser(...) {}
```

## Service Usage

Mark a struct with `@Service` to make it discoverable by the auto-registration generator.

```go
package services

// UserService contains business logic.
// @Service
type UserService struct{}

func NewUserService() *UserService {
	return &UserService{}
}
```

When the generator sees `@Service`:

- If `New<TypeName>()` exists and has zero parameters, that constructor is used
- Otherwise the framework registers `&TypeName{}`
- The service is mapped into the global injector and can be injected later

Add `@Disable` if you want the generator to skip a discovered service, controller, or middleware.

## Middleware Usage

### Define a middleware

```go
package middlewares

import (
	"github.com/linxlib/fw/v2/context"
	"github.com/linxlib/fw/v2/middleware"
)

// AuthMiddleware checks authentication.
// @Middleware
// @Global
type AuthMiddleware struct{}

func (AuthMiddleware) Spec() middleware.AnnotationSpec {
	return middleware.AnnotationSpec{
		Name:  "Auth",
		Scope: middleware.ScopeBoth,
		Stage: middleware.StageBefore,
	}
}

func (AuthMiddleware) Handle(ctx context.Context, args middleware.AnnotationArgs, next middleware.Handler) error {
	return next(ctx)
}
```

### Middleware scopes

- `middleware.ScopeController`: can be used on controller annotations only
- `middleware.ScopeMethod`: can be used on method annotations only
- `middleware.ScopeBoth`: can be used on both

### Middleware stages

- `middleware.StageBefore`: before-handler behavior
- `middleware.StageAfter`: after-handler behavior
- `middleware.StageBoth`: before and after

### Execution order

Execution is deterministic:

1. Global before
2. Controller before
3. Method before
4. Handler
5. Method after
6. Controller after
7. Global after

### Binding and override rules

- Middleware is matched by annotation name
- At the same level, the last annotation with the same name wins
- Method-level middleware overrides controller-level middleware with the same name
- Different middleware names are merged

### Ignore middleware

Use `@Ignore(...)` on a controller method to skip middleware.

```go
// @GET /health
// @Ignore(Auth,Global)
func (c *UserController) Health(ctx context.Context) error {
	return ctx.Respond(fasthttp.StatusOK, 0, "healthy", nil)
}
```

Notes:

- `@Ignore(Auth)` ignores a specific middleware
- `@Ignore(Global)` ignores all global middleware
- Multiple `@Ignore(...)` annotations are merged

### `@Global` behavior

`@Global` is used by the auto-registration generator. When a middleware has both `@Middleware` and `@Global`, generated code calls `e.Use(...)`. Without `@Global`, generated code calls `e.RegisterMiddleware(...)` and the middleware only runs when referenced by annotations.

### Annotation arguments inside middleware

The framework passes annotation values into `middleware.AnnotationArgs`.

```go
// @Auth(role=admin)
```

Inside middleware:

```go
func (AuthMiddleware) Handle(ctx context.Context, args middleware.AnnotationArgs, next middleware.Handler) error {
	role := args.KV["role"]
	_ = role
	return next(ctx)
}
```

### OpenAPI security integration

If a middleware implements `middleware.SecurityProvider`, FW automatically adds the corresponding security scheme to OpenAPI and marks protected routes with a lock.

## Dependency Injection

FW has two injector layers:

- Global injector: app-level services and shared objects
- Request injector: per-request values and request-specific bindings

### Global injection

You can map values manually:

```go
e.Container().Map(NewUserService())
```

Controllers also receive zero-value field injection from the global container when they are registered.

### Struct field injection

The injector supports struct field injection with `inject` tags.

```go
type MyHandler struct {
	Service *UserService `inject:""`
}
```

### Handler parameter injection

At request time, handler method arguments can be resolved from:

- `context.Context` from FW's `context` package
- `*context.FWContext`
- `*fasthttp.RequestCtx`
- Services from the injector
- Primitive values from path, query, or headers
- Struct or pointer-to-struct values from body, query, path, or headers

Example:

```go
func (c *UserController) Create(ctx context.Context, body CreateUserBody, svc *UserService) error {
	return ctx.Respond(fasthttp.StatusOK, 0, "ok", svc.Create(body))
}
```

## Parameter Binding

FW infers parameter sources automatically, but you can guide it with annotations and struct tags.

### Automatic inference rules

For each handler parameter:

1. If the parameter type has `@Query`, `@Path`, `@Header`, or `@Body`, that source is used
2. Otherwise, a type name ending with `Query`, `Path`, `Header`, or `Body` is used as a hint
3. Otherwise, if the parameter name matches a route param like `:id`, it is treated as a path param
4. Otherwise, resolved struct types default to body binding
5. Other primitive values default to query binding

### Primitive binding

Primitive arguments are parsed from strings into:

- `string`
- `bool`
- signed integers
- unsigned integers
- floating-point values
- pointers to those primitive types

Example:

```go
// @GET /users/:id
func (c *UserController) Detail(ctx context.Context, id int, verbose bool) error {
	// id comes from path
	// verbose comes from query
	return nil
}
```

### Struct binding

Struct and pointer-to-struct parameters can be filled from:

- JSON body
- query parameters
- path parameters
- headers

Binding tags:

- `query:"name"`
- `path:"id"`
- `header:"x-trace-id"`
- `json:"name"`

Example:

```go
// CreateUserBody request payload.
// @Body
type CreateUserBody struct {
	Name string `json:"name"`
	Age  int    `json:"age"`
}
```

```go
func (c *UserController) Create(ctx context.Context, body CreateUserBody) error {
	return ctx.Respond(fasthttp.StatusOK, 0, "ok", body)
}
```

Example query model:

```go
// ListUserQuery request query.
// @Query
type ListUserQuery struct {
	Keyword string `query:"keyword"`
	Page    int    `query:"page"`
}
```

```go
func (c *UserController) List(ctx context.Context, query ListUserQuery) error {
	return ctx.Respond(fasthttp.StatusOK, 0, "ok", query)
}
```

## SSE and WebSocket Patterns

The example project shows how method-level middlewares can take over the request flow.

### SSE

The `SSE` middleware starts a Server-Sent Events stream and maps `*context.SSEWriter` into the request container, so handlers can receive it as a parameter.

```go
// @GET /stream
// @SSE
func (c *UserController) Stream(ctx context.Context, w *context.SSEWriter) error {
	return nil
}
```

### WebSocket

The `WS` middleware upgrades the connection, reads messages, maps the current message into the request container, and lets the handler build a reply.

```go
// @GET /ws
// @WS
func (c *UserController) Echo(ctx context.Context, msg []byte) error {
	ctx.Set("WS.Reply", msg)
	return nil
}
```

## Response Model

Default response envelope:

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "trace_id": "..."
}
```

### Normal response

Use the chainable response builder for common cases:

```go
return ctx.StatusOK().Data(data)
```

Examples:

```go
return ctx.StatusOK().Message("saved").Data(result)
return ctx.StatusOK("healthy").Send()
return ctx.StatusParamError("param xx invalid").Send()
return ctx.StatusServerError().Message("").Send()
```

`Respond(statusCode, code, message, data)` is still available when you want to set everything explicitly.

### Automatic response from handler return values

If a handler returns one or more values and does not write a response itself, FW uses the first non-`error` return value as the success payload.

```go
// @GET /profile
func (c *UserController) Profile() map[string]any {
	return map[string]any{"name": "alice"}
}
```

The response is still wrapped by default:

```json
{"code":0,"message":"ok","data":{"name":"alice"}}
```

If the handler returns an `error` result and it is not `nil`, FW treats the request as failed and does not write a success response.

### Raw response with `@RawResponse`

Use `@RawResponse` on a handler method when you want the first non-`error` return value to be written directly.

```go
// @GET /profile/raw
// @RawResponse
func (c *UserController) ProfileRaw() map[string]any {
	return map[string]any{"name": "alice"}
}
```

Response body:

```json
{"name":"alice"}
```

Notes:

- `@RawResponse` is method-only behavior
- It only affects framework-managed automatic writes from return values
- If the handler or middleware already wrote a response, FW does not overwrite it
- `ctx.Respond(...)` and `ctx.StatusOK()` still use the configured formatter and keep the normal envelope

### Manual raw response with `ctx.RawResponse()`

Use `ctx.RawResponse()` when you want a handler or middleware to write a payload directly without the default envelope.

```go
return ctx.RawResponse().Data("ok")
```

Response body:

```json
"ok"
```

Notes:

- `ctx.RawResponse()` is for manual response writes
- `@RawResponse` is for automatic writes from handler return values
- Both paths still use the configured encoder

### Automatic empty success response

If the handler returns without writing a response and no error occurs, FW writes:

```json
{"code":0,"message":"ok"}
```

### Custom formatter and encoder

You can replace the response formatter and encoder:

```go
e.SetResponse(customFormatter, customEncoder)
```

## OpenAPI and Swagger

When `openapi.enabled` is `true`, FW generates an OpenAPI file during startup and registers documentation routes.

Default routes:

- `/docs`
- `/docs/config`
- `/docs/openapi.json`

### OpenAPI generation includes

- Route path and HTTP method
- Operation ID
- Controller name as tag
- Method description as summary
- Path, query, header, and body parameter schemas
- Basic `200` response schema
- Security requirements from middleware

### Response schema selection

By default, FW uses the first non-`error` return value as the OpenAPI `data` schema.

You can override that with `@Response` on the handler:

```go
// @Response(index=1)
```

Supported forms:

- `@Response(1)`
- `@Response(index=1)`
- `@Response(result=1)`

Positive indexes are 1-based.

If the handler also has `@RawResponse`, OpenAPI uses the selected return value as the top-level `200` response schema directly instead of wrapping it under `data`.

## Configuration

Configuration load order:

1. Built-in defaults
2. YAML file
3. Environment variables with prefix `FW_`

Example config:

```yaml
project_dir: .

server:
  host: "0.0.0.0"
  port: 8080

log:
  level: info
  output: console
  file_path: logs/fw.log
  enable_file: false
  request_enabled: true

recovery:
  enabled: true
  return_stack_to_body: true

openapi:
  enabled: true
  output: openapi.json
  title: "FW API"
  version: "1.0.0"

middlewares:
  authorization:
    api-key: xxxx
```

### Common environment overrides

```bash
FW_SERVER_HOST=127.0.0.1
FW_SERVER_PORT=9090
FW_LOG_LEVEL=debug
FW_OPENAPI_ENABLED=false
```

### Middleware config from environment

Middleware sections can also be overridden by environment variables.

Example:

```bash
FW_MIDDLEWARES_AUTHORIZATION_API_KEY=secret
```

This maps to:

```yaml
middlewares:
  authorization:
    api-key: secret
```

## Recovery and Logging

### Recovery

Recovery is enabled by default.

When a panic happens:

- the framework logs the panic and formatted stack tree
- it returns HTTP `500`
- it writes a standard error envelope
- it can optionally include the stack in the response body

Config:

```yaml
recovery:
  enabled: true
  return_stack_to_body: true
```

### Request logging

When `log.request_enabled` is `true`, FW logs one line per request including method, path, status, and duration.

## Manual Registration

If you do not want to rely on generated auto-registration, you can register components manually.

```go
e, _ := app.New("config/app.yaml")

e.Container().Map(services.NewUserService())
e.Use(&middlewares.AuthMiddleware{})
e.RegisterMiddleware(&middlewares.LogMiddleware{})
e.RegisterController(&controllers.UserController{})
```

## `cmd/fw` CLI

The framework includes a CLI under `cmd/fw`.

Run locally from this repository:

```bash
go run ./cmd/fw --help
```

You can also install it:

```bash
go install github.com/linxlib/fw/v2/cmd/fw@latest
```

### `fw init`

Create a new project:

```bash
fw init myapp
```

Or initialize inside the current directory:

```bash
fw init
```

Notes:

- `fw init` without a project name requires the current directory to be basically empty
- The generated module name defaults to the directory or project name

### `fw build`

Build the current project:

```bash
fw build
```

Build another directory:

```bash
fw build ./cmd/server
fw build --dir ./cmd/server
```

Cross-compile:

```bash
fw build -os linux -arch amd64
fw build -os macos -arch arm64 -o app
fw build -os windows -arch amd64 -o demo.exe
```

Flags:

- `-o, --output`: output binary name
- `--os`: target OS, supports `windows`, `linux`, `macos`
- `--arch`: target architecture, supports `amd64`, `arm64`
- `--dir`: working directory

Behavior details:

- On Windows targets, `.exe` is added automatically if missing
- On non-Windows targets, `.exe` is removed from the output name
- Cross-compilation sets `CGO_ENABLED=0`

### `fw create`

Generate framework components:

```bash
fw create controller --name User --route /api/v1/users
fw create service --name User
fw create middleware --name Authorization
```

Subcommands:

- `fw create controller`
- `fw create service`
- `fw create middleware`

Notes:

- If `--name` is omitted, the command switches to interactive prompts
- Names must start with a letter and contain only letters or digits
- Files are created under `controllers/`, `services/`, and `middlewares/`
- Existing files are not overwritten

### `fw version`

```bash
fw version
```

### `fw completion`

Because the CLI uses Cobra, a `completion` command is also available:

```bash
fw completion bash
fw completion zsh
```

## Recommended Development Flow

1. Run `fw init your-app`
2. Add controllers, services, and middlewares
3. Mark them with `@Controller`, `@Service`, `@Middleware`
4. Run `fw build` to regenerate AST metadata and the auto-registration file
5. Run `go run .` during development
6. Open `/docs` to inspect the generated API documentation
7. Run `go test ./...` before shipping changes

## Example Controller With Multiple Features

```go
package controllers

import (
	"github.com/your/mod/models"
	"github.com/your/mod/services"
	"github.com/linxlib/fw/v2/context"
	"github.com/valyala/fasthttp"
)

// UserController handles user APIs.
// @Controller
// @Route /api/v1/users
// @Authorization(Admin)
type UserController struct {
	Service *services.UserService
}

// Update updates a user.
// @POST /:id
// @Log(stage=before)
func (c *UserController) Update(ctx context.Context, id int, body models.UpdateUserBody) error {
	return ctx.Respond(fasthttp.StatusOK, 0, "ok", map[string]any{
		"id":   id,
		"body": body,
	})
}

// Health returns service health.
// @GET /health
// @Ignore(Authorization,Global)
func (c *UserController) Health(ctx context.Context) error {
	return ctx.Respond(fasthttp.StatusOK, 0, "healthy", nil)
}
```

## Summary

FW is best suited for teams that want:

- Simple API development with less boilerplate
- Annotation-style route and middleware declarations
- Automatic DI and request parameter binding
- OpenAPI generation without writing schemas by hand
- A small toolchain for scaffolding and build automation
